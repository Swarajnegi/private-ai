Q&A #001

L2 Normalization

📅 March 7, 2026 📂 Sub-Phase 2.1 — Embeddings & Similarity
math embeddings cosine-similarity vector-search

❓ What is L2 normalization and why does JARVIS need it?

1 The Intuition

L2 normalization stretches or shrinks a vector so its length becomes exactly 1.0, while keeping it pointing in the same direction.

Think of two arrows in space. One is 3 meters long, the other is 10 meters long. L2 normalization resizes both to exactly 1 meter — now you can fairly compare their direction without the longer arrow having an unfair advantage.

Before normalization: Vector A: [3, 4] → length = √(3² + 4²) = √25 = 5.0 Vector B: [6, 8] → length = √(6² + 8²) = √100 = 10.0 These point in the SAME direction but have different lengths. dot(A, B) = 3×6 + 4×8 = 50 (big number, but misleading) After L2 normalization: Vector A: [3/5, 4/5] = [0.6, 0.8] → length = 1.0 Vector B: [6/10, 8/10] = [0.6, 0.8] → length = 1.0 Now they're IDENTICAL — they always pointed the same way. dot(A, B) = 0.6×0.6 + 0.8×0.8 = 1.0 (= cosine similarity!)

The "L2" Part

It refers to the L2 norm (Euclidean norm) — the formula for vector length. The "2" means you square each element.

‖v‖₂ = √( v₁² + v₂² + v₃² + … + v₃₈₄² )

2 The JARVIS Application

Imagine you ask JARVIS: "How do I use async generators?"

JARVIS embeds your query and 5,000 stored document chunks. Without normalization:

Query embedding: length = 8.2 Short chunk (1 line): length = 3.1 Long chunk (200 words): length = 12.7 dot(query, short) = 25.4 dot(query, long) = 104.6 ◄── WINS, but only because it's LONGER

The long chunk wins purely because its magnitude is bigger — not relevance. This is magnitude bias.

After L2 normalization:

Query embedding: length = 1.0 Short chunk: length = 1.0 Long chunk: length = 1.0 dot(query, short) = 0.87 ◄── ACTUALLY more relevant dot(query, long) = 0.42
✅

Now dot product = cosine similarity. Only direction matters.

The Performance Win

Search Method Operations per Query (100K docs) Speed
Cosine similarity (unnormalized) 100K dots + 200K norms = 300K ops Baseline
Dot product (pre-normalized) 100K dots = 100K ops 3× faster

ChromaDB normalizes at storage time, then uses fast dot product for search.

3 The Code

import numpy as np

def l2_normalize(v: np.ndarray) -> np.ndarray:
    """
    Math: v̂ = v / ‖v‖₂
    After this: ‖v̂‖₂ = 1.0
    """
    norm = np.linalg.norm(v)   # √(v₁² + v₂² + … + vₙ²)
    if norm == 0:
        return v
    return v / norm


# ─── Demo ────────────────────────────────────────
v = np.array([3.0, 4.0])
v_norm = l2_normalize(v)
print(np.linalg.norm(v_norm))  # 1.0


# ─── The cosine shortcut ─────────────────────────
a = np.array([3.0, 4.0, 1.0])
b = np.array([1.0, 2.0, 3.0])

# Full cosine (expensive — 3 operations):
cosine = np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b))

# Pre-normalize once, then dot (cheap — 1 operation):
a_n = l2_normalize(a)
b_n = l2_normalize(b)
print(np.dot(a_n, b_n))  # Same as cosine!

In sentence-transformers

# Embed WITH normalization (recommended for ChromaDB):
embeddings = model.encode(texts, normalize_embeddings=True)

# Now ‖embedding‖₂ = 1.0 for ALL vectors
# And np.dot(a, b) = cosine_similarity(a, b)

4 The Gotchas

Zero Vector Division

⚠️

If a text produces an all-zero embedding, L2 normalization divides by zero. Guard with if norm < 1e-9.

Magnitude Information Lost

Normalization destroys magnitude. Fine for RAG (you only care about direction), but bad for anomaly detection where unusual magnitude = unusual input.

L2 vs Other Norms

Norm Formula Name JARVIS?
L1 |v₁| + |v₂| + … + |vₙ| Manhattan No
L2 ◀ √(v₁² + v₂² + … + vₙ²) Euclidean Yes
L∞ max(|v₁|, …, |vₙ|) Max element No
📌

For embeddings, always L2. It's what cosine similarity assumes, and what sentence-transformers and ChromaDB expect.

❓ What does max_seq_length: 256 mean? What are ##ron and ##ous tokens? What are positional embeddings? What happens when the model "silently drops" tokens? How do BERT and MiniLM compare? Why is batch encoding 2-4× faster?

1 BERT vs all-MiniLM-L6-v2: The Family Tree

all-MiniLM-L6-v2 is not a separate model architecture. It is a compressed, distilled version of BERT. Think of BERT as the teacher and MiniLM as the student who learned to do 90% of the teacher's work in 25% of the time.

Key: They use the exact same tokenizer (WordPiece, same vocabulary). The difference is in the transformer body, not in how text is split into tokens. MiniLM just has fewer layers and narrower hidden dimensions.

JARVIS Verdict

For the Memory Layer (Stage 2), MiniLM wins. You get 97% of BERT's quality at 20% of the cost. BERT-base is too heavy for an embedding model that runs on every document chunk and every user query. You'd only consider BERT-base if you were fine-tuning for a specific domain (Stage 5+).

2 WordPiece Tokenization (What ## Means)

Before any text enters the transformer, it must be converted from human-readable words into token IDs — integers that the model can process. This conversion is called tokenization.

Both BERT and MiniLM use the WordPiece algorithm. Here's the core idea:

The Problem WordPiece Solves

If the vocabulary only contained whole words, you'd need millions of entries to cover every word in every language, plus typos, code syntax, technical jargon, etc. That would make the token embedding table impossibly large.

Instead, WordPiece builds a vocabulary of 30,522 subword pieces. Common words like "the", "how", "work" get their own entry. Rare or long words get split into known pieces.

The ## Prefix Explained

The ## prefix means "this piece continues the previous token — it is NOT a new word."

Word: "asynchronous" Not in the 30,522 vocab as a whole word. WordPiece splits it: "as" → Token ID 2004 (no ## = start of a new word) "##yn" → Token ID 17589 (## = continuation of previous word) "##ch" → Token ID 15387 (## = still continuing) "##ron"→ Token ID 6444 (## = still continuing) "##ous"→ Token ID 7140 (## = final piece) The model sees 5 tokens, but knows they form ONE word because of ## Compare with a common word: "generators" → Token ID 19529 (single token — it's common enough) "work" → Token ID 2147 (single token)
⚠️

Critical implication for token counting: The word "asynchronous" uses 5 tokens, not 1. A sentence with many technical/rare words burns through the 256-token budget much faster than plain English. Code snippets are especially expensive.

More Examples

Common words (1 token each): "the" → [the] "python" → [python] "model" → [model] Technical words (multiple tokens): "embedding" → [em, ##bed, ##ding] 3 tokens "backpropagation" → [back, ##pro, ##pa, ##gation] 4 tokens "ChromaDB" → [chroma, ##db] 2 tokens Special tokens (always added): [CLS] → Added at the START of every input (classification token) [SEP] → Added at the END of every input (separator token) So "Hello world" actually becomes: [[CLS], hello, world, [SEP]] = 4 tokens (2 words + 2 special)

Token → ID → Embedding

The full pipeline from text to numbers:

Step 1: "async generators" → [[CLS], as, ##yn, ##ch, ##ron, ##ous, generators, [SEP]] Step 2: Token strings → IDs: [101, 2004, 17589, 15387, 6444, 7140, 19529, 102] Step 3: Each ID → lookup in Token Embedding Table (30,522 × 384) ID 2004 → row 2004 of the table → a specific 384-dim vector ID 17589 → row 17589 → a different 384-dim vector ... Step 4: Each token also gets a Positional Embedding added (see next section)

3 Positional Embeddings — Why Order Matters

The Problem

Unlike RNNs that process tokens one-by-one (left to right), a Transformer processes all tokens simultaneously in one parallel matrix multiplication. This means by default, it has no concept of order. The sentences "dog bites man" and "man bites dog" would look identical — same tokens, same embeddings, same result.

The Solution: A Position Lookup Table

The model has a second embedding table — not for what the token is, but for where it is. This is the Positional Embedding Table.

Two separate lookup tables: Token Embedding Table (30,522 rows × 384 columns) Row 2004 → vector for "as" (WHAT this token means) Row 17589 → vector for "##yn" (WHAT this token means) Row 19529 → vector for "generators" (WHAT this token means) Position Embedding Table (512 rows × 384 columns) Row 0 → vector for "I am the 1st token" (WHERE this token sits) Row 1 → vector for "I am the 2nd token" (WHERE this token sits) Row 2 → vector for "I am the 3rd token" (WHERE this token sits) ... Row 255 → vector for "I am the 256th token" Row 256+ → EXISTS in BERT (512 max) but MiniLM limits to 256 Final input to transformer = Token Embedding + Position Embedding token_embed[2004] + position_embed[0] = "as" at position 0 token_embed[17589] + position_embed[1] = "##yn" at position 1 ...

What "Learned" Means

These position vectors are not hand-coded. During training, the model was shown millions of sentences and learned (via backpropagation — the same gradient descent you already know) what each position vector should be. Position 0 learned "tokens here are usually [CLS] or sentence starters." Position 255 learned "tokens here are usually near the end of a passage."

The table has a fixed number of rows — it was created before training started with exactly 512 rows (for BERT) or 256 usable rows (for MiniLM). There is no row 257. It's like an array with 256 slots — accessing index 256 is out of bounds.

Why MiniLM Uses 256, Not 512

BERT's position table has 512 rows. MiniLM inherits this table (it was distilled from BERT), but the sentence-transformers library sets max_seq_length = 256 as a software limit. Why? Because MiniLM was specifically trained/distilled for short text (sentences, paragraphs) and its quality degrades significantly beyond 256 tokens. The library truncates at 256 to prevent you from getting bad embeddings from positions the model wasn't optimized for.

4 Silent Truncation — What Actually Happens

"Silent truncation" means the model cuts off your text without telling you. Here's the exact mechanical sequence:

You give the model a 400-word document: Step 1: Tokenize 400 words → WordPiece → 674 tokens (Technical text often produces more tokens than words due to ## splitting) Step 2: Truncate (THE SILENT PART) The tokenizer checks: 674 > max_seq_length (256) Action: Keep tokens [0..255], DISCARD tokens [256..673] No error raised. No warning printed. (The warning you saw in the script output is from the underlying HuggingFace tokenizer, but sentence-transformers suppresses it in normal usage) Step 3: Process Only the first 256 tokens enter the transformer. The transformer produces a 384-dim embedding based on ONLY what it saw — the first ~200 words. Step 4: Output You get back ONE 384-dim vector. This vector represents the FIRST 200 words only. The remaining 200 words do not exist as far as this embedding is concerned.

The Real-World Danger

Imagine a research paper chunk: Words 1-200 (kept): "In this paper, we present background information on transformer architectures. Transformers were introduced by Vaswani et al. in 2017 and have since become the dominant architecture for natural language processing tasks..." Words 201-400 (SILENTLY DISCARDED): "Our key finding is that speculative decoding achieves 2.8× speedup with zero quality loss when using a 3B draft model paired with a 70B verifier. This makes real-time inference feasible on consumer GPUs with 48GB VRAM..." The embedding captures "background on transformers" but completely misses the actual key finding. If you search "speculative decoding speedup" → this chunk will NOT be found.
⚠️

This is the #1 cause of "JARVIS can't find the answer even though it's in the documents" — the answer was in the truncated part of a chunk that was too long.

6 Batch vs Sequential Encoding

Sequential encoding calls the model once per text. Each call has fixed overhead (Python→C++ bridge, memory allocation, tensor setup). You pay that overhead N times. Batch encoding stacks all texts into one tensor and runs the transformer once on the entire batch.

Sequential (100 texts): Call 1: [overhead] + [compute for 1 text] → 13ms × 100 = 1,300ms Batched (batch_size=32): Batch 1-3: [overhead] + [compute for 32 texts] → 140ms each Batch 4: [overhead] + [compute for 4 texts] → 50ms Total: 470ms (= 2.8× faster)

Matrix multiplication on GPUs/modern CPUs is parallelized at the hardware level. Multiplying a (32, 256, 384) tensor costs almost the same wall-clock time as a (1, 256, 384) tensor — the silicon does 32 operations simultaneously. 

# SLOW (100 Python→C++ roundtrips):
for text in texts:
    emb = model.encode(text)      # 13ms each × 100 = 1,300ms

# FAST (4 roundtrips):
embs = model.encode(texts, batch_size=32)  # ~470ms total

Rule: Always batch at ingestion time. Only encode one-at-a-time at query time (single user question).

1 The Paper That Started It All

"Attention Is All You Need" (Vaswani et al., June 2017, Google Brain) proposed the Transformer — an architecture using only attention, no RNNs, no convolutions. This single paper is the foundation of GPT, BERT, MiniLM, Llama, and every modern LLM.

Key difference: The paper's original transformer had both encoder AND decoder (for translation). BERT/MiniLM use encoder only. GPT/Llama use decoder only. Same building blocks, different selection.

2 Where The Input Actually Comes From

Using the two-paragraph example that exposes the critical invisible operation: the model has zero awareness of sentence boundaries inside a string.

para_1 = "Generators yield values lazily. They save RAM. The OS loves them. Python uses them everywhere. JARVIS needs them."
para_2 = "Async adds concurrency. The event loop schedules tasks. Await pauses a coroutine. Gather runs tasks in parallel. Callbacks are legacy. Promises evolved."
embeddings = model.encode([para_1, para_2])
# You passed 2 strings. The model sees 2 items — NOT 11 sentences.
STEP 1 — TOKENIZE (each string independently) String 0 (para_1 — 5 sentences, but tokenizer doesn't care about "." as boundary): [CLS] generators yield values la ##zi ##ly . they save ram . the os loves them . python uses them every ##where . jar ##vis needs them . [SEP] → ~27 token IDs Periods are regular tokens, NOT sentence breaks. String 1 (para_2 — 6 sentences): [CLS] as ##yn ##c adds con ##cur ##ren ##cy . the event loop schedules tasks . await pauses a co ##ro ##uti ##ne . gather runs tasks in parallel . call ##back ##s are legacy . promises evolved . String 0 gets 13 [PAD] tokens appended so both have length 40. attention_mask marks real tokens (1) vs padding (0): String 0: [CLS, generators, ..., them, ., SEP, PAD, PAD, ..., PAD] ←───── 27 real tokens ─────→ ←──── 13 padding ────→ mask: [1, 1, 1, ..., 1, 1, 1, 0, 0, ..., 0 ] String 1: [CLS, as, ##yn, ##c, ..., evolved, ., SEP] ←────────── 40 real tokens (no padding) ──────────→ mask: [1, 1, 1, 1, ..., 1, 1, 1] Combined batch tensor: shape (2, 40) — 2 strings, 40 token IDs each
STEP 2 — EMBED (lookup tables) Token Embedding Table: (30,522 rows × 384 cols) Each of the 40 token IDs looks up its 384-dim row. Position Embedding Table: (512 rows × 384 cols) Position 0 → row 0, Position 1 → row 1, ..., Position 39 → row 39 (Table has 512 rows — BERT inheritance. Sentence-transformers clips at 256.) Final = token_embed + position_embed (element-wise addition) Output: (2, 40, 384) │ │ └── 384 floats per token │ └── 40 tokens per string (padded) └── 2 strings in the batch ← THIS enters the transformer
📄

Paper note (§3.5): The original paper used sinusoidal positional encodings (sine/cosine waves of different frequencies), not learned lookup tables. They found learned embeddings produce "nearly identical results" (Table 3, row E). BERT/MiniLM chose learned embeddings. Modern models like Llama use RoPE (rotary).

Result: The input to the transformer is a tensor of shape (2, 40, 384). Two strings, padded to 40 tokens each, 384 floats per token. These are the numbers that Q, K, V projections operate on.

3 Self-Attention — Full Numerical Walkthrough

Using 3 tokens from para_1, 4 dimensions so every number is visible. The math is identical to 40 tokens × 384 dims — just bigger matrices.

⚠️

CRITICAL: Attention operates WITHIN each string, NOT across strings. String 0's tokens attend ONLY to string 0's other tokens. String 1's tokens attend ONLY to string 1's other tokens. The two paragraphs NEVER see each other. The batch dimension (2) is processed in parallel but independently.

Step 0: The Input (3 tokens from para_1, after embedding + position)

X = 3 tokens × 4 dimensions (from string 0 / para_1): dim0 dim1 dim2 dim3 "generators" [ 0.5 1.0 -0.5 0.2 ] "yield" [ -0.3 0.8 0.4 0.7 ] "values" [ 0.6 -0.2 0.9 -0.1 ] Shape: (3, 4) — one string only. String 1 runs the same math independently.

Step 1: Creating Q, K, V — Why (4×4)?

The model has 3 weight matrices: Wq, Wk, Wv. Each is (4, 4) because input has 4 dimensions and output has 4 dimensions. For MiniLM: input has 384 dims, output has 384 dims → Wq is (384, 384). That's why.

What "Learned" Means (Precisely)

Before training: W_q = random values from Gaussian distribution, e.g. N(0, 0.02) W_k = different random values W_v = different random values During training (millions of iterations): 1. Forward pass: compute attention with current weights 2. Compute loss (how bad the embedding/prediction is) 3. Backward pass: backprop computes ∂Loss/∂W_q, ∂Loss/∂W_k, ∂Loss/∂W_v 4. Update: W_q = W_q - lr × gradient After training: Weights converge to values that produce good attention patterns. Same process as training a CNN. Different architecture, same backprop. γ, β in LayerNorm are also "learned" this exact same way.

Step 1b: Actual Matrix Multiplication for Q

W_q (Query weights — learned during training): out0 out1 out2 out3 in0 [ 0.1 0.3 -0.2 0.4 ] in1 [ 0.5 -0.1 0.2 0.0 ] in2 [ -0.3 0.4 0.6 -0.1 ] in3 [ 0.2 0.0 -0.4 0.3 ] Computing Q for "generators" = [0.5, 1.0, -0.5, 0.2] × W_q: Q_gen[0] = (0.5×0.1) + (1.0×0.5) + (-0.5×-0.3) + (0.2×0.2) = 0.05 + 0.50 + 0.15 + 0.04 = 0.74 Q_gen[1] = (0.5×0.3) + (1.0×-0.1) + (-0.5×0.4) + (0.2×0.0) = 0.15 + (-0.10) + (-0.20) + 0.00 = -0.15 Q_gen[2] = (0.5×-0.2) + (1.0×0.2) + (-0.5×0.6) + (0.2×-0.4) = -0.10 + 0.20 + (-0.30) + (-0.08) = -0.28 Q_gen[3] = (0.5×0.4) + (1.0×0.0) + (-0.5×-0.1) + (0.2×0.3) = 0.20 + 0.00 + 0.05 + 0.06 = 0.31 Q_gen = [0.74, -0.15, -0.28, 0.31] ← ONE row of Q

Same multiplication for all tokens produces the full matrices:

Full Q matrix = X × W_q (3×4) × (4×4) = (3×4): q0 q1 q2 q3 Q_gen [ 0.74 -0.15 -0.28 0.31 ] Q_yld [ 0.31 0.42 0.18 0.05 ] Q_val [ 0.02 0.58 0.42 -0.07 ] Full K matrix = X × W_k: k0 k1 k2 k3 K_gen [ 0.13 0.24 -0.39 0.29 ] K_yld [ 0.15 0.23 -0.21 0.20 ] K_val [ 0.34 -0.11 -0.37 0.38 ] Full V matrix = X × W_v: v0 v1 v2 v3 V_gen [-0.01 0.55 -0.55 0.40 ] V_yld [ 0.14 0.28 0.47 0.39 ] V_val [ 0.38 -0.21 0.36 -0.01 ]

Step 2: Attention Scores — Every Dot Product Shown

Score[gen→gen] = Q_gen · K_gen: = (0.74×0.13) + (-0.15×0.24) + (-0.28×-0.39) + (0.31×0.29) = 0.096 + (-0.036) + 0.109 + 0.090 = 0.259 Score[gen→yld] = Q_gen · K_yld: = (0.74×0.15) + (-0.15×0.23) + (-0.28×-0.21) + (0.31×0.20) = 0.111 + (-0.035) + 0.059 + 0.062 = 0.197 Score[gen→val] = Q_gen · K_val: = (0.74×0.34) + (-0.15×-0.11) + (-0.28×-0.37) + (0.31×0.38) = 0.252 + 0.017 + 0.104 + 0.118 = 0.491 Full Scores matrix Q×KT = (3×4) × (4×3) = (3×3): gen yld val gen → [ 0.259 0.197 0.491 ] ← gen attends most to val yld → [ 0.168 0.143 0.240 ] ← yld attends most to val val → [ 0.312 0.198 0.521 ] ← val attends most to itself

Step 3: Scale by √dk

d_k = 4, √4 = 2.0. Scaled = Scores / 2.0: gen yld val gen → [ 0.130 0.099 0.246 ] yld → [ 0.084 0.072 0.120 ] val → [ 0.156 0.099 0.261 ]
📄

Paper §3.2.1: "for large values of dk, the dot products grow large in magnitude, pushing the softmax function into regions where it has extremely small gradients." For dk=64, dot products would have std dev = 8. Dividing by √64=8 brings variance back to 1.

Step 4: Softmax (Row → Probabilities)

Softmax for row "generators": softmax([0.130, 0.099, 0.246]) e0.130 = 1.139, e0.099 = 1.104, e0.246 = 1.279, sum = 3.522 softmax = [1.139/3.522, 1.104/3.522, 1.279/3.522] = [0.323, 0.313, 0.363] sums to 1.0 ✓ Full Attention Weights: gen yld val gen → [ 0.323 0.313 0.363 ] ← 36.3% attention to "values" yld → [ 0.340 0.333 0.327 ] ← roughly equal val → [ 0.317 0.292 0.391 ] ← 39.1% to itself

Step 5: Weighted Sum of Values

Output for "generators" = 0.323 × V_gen + 0.313 × V_yld + 0.363 × V_val dim0: (0.323×-0.01) + (0.313×0.14) + (0.363×0.38) = 0.179 dim1: (0.323×0.55) + (0.313×0.28) + (0.363×-0.21) = 0.190 dim2: (0.323×-0.55) + (0.313×0.47) + (0.363×0.36) = 0.100 dim3: (0.323×0.40) + (0.313×0.39) + (0.363×-0.01) = 0.247 Output_gen = [0.179, 0.190, 0.100, 0.247] "generators" is no longer just "generators". It now carries blended information from the entire sentence.
📐

The Formula: Attention(Q, K, V) = softmax(Q × KT / √dk) × V
Each token's output is a weighted average of ALL other tokens' values, weighted by Q·K similarity.

4 Multi-Head Attention — Paper's Exact Formula

One attention head learns ONE type of relationship. But language has many: syntactic, semantic, positional. Solution: Run multiple heads in parallel:

Paper §3.2.2 formula: MultiHead(Q, K, V) = Concat(head₁, ..., headₕ) × WO where headᵢ = Attention(X × WᵢQ, X × WᵢK, X × WᵢV) MiniLM: 384-dim, 6 heads → each head: 384 / 6 = 64 dimensions Head 1: Q₁(8,64), K₁(8,64), V₁(8,64) → Out₁(8,64) [learns syntax] Head 2: Q₂(8,64), K₂(8,64), V₂(8,64) → Out₂(8,64) [learns semantics] ... Head 6: Q₆(8,64), K₆(8,64), V₆(8,64) → Out₆(8,64) [learns position] Concatenate: [Out₁ | Out₂ | ... | Out₆] → (8, 384) Output projection: (8, 384) × WO(384, 384) = (8, 384)

5 FFN — Feed-Forward Network

Paper §3.3 formula: FFN(x) = max(0, x × W₁ + b₁) × W₂ + b₂ With actual shapes: x: (3, 4) ← 3 tokens, 4 dims W₁: (4, 16) ← "up-project" to 4× wider (d_ff = 4 × d_model) hidden: (3, 16) ← 4× wider intermediate ReLU: element-wise ← negative values → 0 W₂: (16, 4) ← "down-project" back output: (3, 4) ← same shape as input MiniLM: W₁ is (384×1536), W₂ is (1536×384)
⚠️

Why FFN exists: Attention is linear — weighted sums. Stacking linear operations = still linear. FFN adds non-linearity (ReLU/GELU). Without it, 6 attention layers = 1 attention layer.
Note: Paper uses ReLU. BERT/MiniLM use GELU. Llama uses SiLU + gating.

6 LayerNorm — Every Variable Explained

Formula: output = γ × ((x - μ) / (σ + ε)) + β Every variable: x = input vector for ONE token: [0.179, 0.190, 0.100, 0.247] μ (mu) = mean = (0.179 + 0.190 + 0.100 + 0.247) / 4 = 0.179 σ (sigma) = standard deviation = 0.052 ε (epsilon) = 1e-5 (prevents division by zero) Normalize (zero mean, unit variance): x_norm[0] = (0.179 - 0.179) / (0.052 + 1e-5) = 0.000 x_norm[1] = (0.190 - 0.179) / (0.052 + 1e-5) = 0.212 x_norm[2] = (0.100 - 0.179) / (0.052 + 1e-5) = -1.519 x_norm[3] = (0.247 - 0.179) / (0.052 + 1e-5) = 1.308 γ (gamma) = LEARNED per-dimension SCALE Init: [1, 1, 1, 1] After training: [0.93, 1.12, 0.87, 1.05] β (beta) = LEARNED per-dimension SHIFT Init: [0, 0, 0, 0] After training: [0.02, -0.08, 0.05, 0.01] Apply scale + shift: output[0] = 0.93 × 0.000 + 0.02 = 0.020 output[1] = 1.12 × 0.212 + (-0.08) = 0.157 output[2] = 0.87 × (-1.519) + 0.05 = -1.271 output[3] = 1.05 × 1.308 + 0.01 = 1.383
💡

Why γ and β exist: Pure normalization forces mean=0, variance=1. But maybe some dimensions SHOULD have larger values. γ and β give the model the option to undo normalization if optimal.
Params: 384 (γ) + 384 (β) = 768 params per LayerNorm.

7 Residual Connections — The Gradient Highway

From paper §3.1: "the output of each sub-layer is LayerNorm(x + Sublayer(x))"

Residual = ADD the original input back: output = x + f(x) NOT just f(x) Concrete example: x = [0.42, -0.03, 0.13, -0.26] ← original token embedding attn_out = [0.179, 0.190, 0.100, 0.247] ← attention's result RESIDUAL ADD: residual = [0.42+0.179, -0.03+0.190, 0.13+0.100, -0.26+0.247] = [0.599, 0.160, 0.230, -0.013] THEN LayerNorm(residual) → the γ/β/μ/σ process from section 6

Why Residuals Are Critical

Reason 1: Gradient Highway ∂(x + f(x))/∂x = 1 + ∂f(x)/∂x That "1 +" is the highway. Even if ∂f(x)/∂x → 0, gradient ≥ 1. Reason 2: Identity Baseline If attention/FFN outputs zeros: output = x + 0 = x The model can't make things WORSE by adding layers.
📄

Paper §3.1: "To facilitate these residual connections, all sub-layers produce outputs of dimension dmodel=512." This is why every layer has the same dimension — the addition x+f(x) requires matching shapes.

The Key Difference: Causal Masking

12 JARVIS Lifecycle — Where Transformers Live

You ask JARVIS: "How do async generators work?" PHASE 1: EMBEDDING (MiniLM — Encoder Transformer) ├─ Tokenize question → 8 token IDs ├─ Lookup token embeds + add position embeds ├─ Run through 6 transformer layers (attention → FFN × 6) ├─ Mean pool 8 token vectors → 1 vector (384-dim) ├─ L2 normalize → unit length └─ This vector = your question's "meaning" in numbers PHASE 2: RETRIEVAL (ChromaDB — cosine similarity) ├─ Compare question vector vs ALL stored doc chunk vectors ├─ Top 5 most similar chunks retrieved └─ These are the "relevant context" PHASE 3: GENERATION (Llama 70B — Decoder Transformer) ├─ Prompt = "Context: [5 chunks]. Question: ..." ├─ Run through 80 transformer layers (SAME Q,K,V math) │ but with CAUSAL MASK (can only see previous tokens) ├─ At each step, predict NEXT token └─ "Async" → "generators" → "are" → ... (the response) TWO transformers, TWO roles: MiniLM (encoder): text → vector (for search) Llama (decoder): prompt → text (for response) Same Q,K,V building blocks. Different mask. Different output.
